# VPC Provisioning API

A REST API that creates AWS VPCs with multiple subnets, stores the result, and serves it
back. Python, FastAPI, boto3, DynamoDB. Authenticated with OAuth2 bearer tokens.

The same image runs under `uvicorn` locally and as a Lambda container image in AWS,
deployed by Terraform through GitHub Actions.

```
client ──Bearer JWT──▶ FastAPI  (uvicorn locally / Lambda + Mangum in AWS)
                          │
              routers ──▶ services ──▶ boto3 ec2       ─▶ VPC, subnets, IGW, routes
                                   └─▶ boto3 dynamodb  ─▶ networks table
```

The layering exists so the AWS calls are testable in isolation: routers do HTTP and
validation, services own orchestration, and nothing else touches boto3.

---

## Quickstart

```bash
cp .env.example .env
docker compose up --build
```

The API is on <http://localhost:8000>, interactive docs at <http://localhost:8000/docs>.

This runs against **real EC2** (using your host's AWS credentials, mounted read-only)
and **local DynamoDB**, so you get real VPCs without needing to provision a table.

Get a token and create a network:

```bash
TOKEN=$(curl -s -X POST http://localhost:8000/v1/auth/token \
  -d 'username=demo&password=demo-password' | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')

curl -X POST http://localhost:8000/v1/networks \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "demo-network",
    "cidr_block": "10.0.0.0/16",
    "subnets": [
      {"name": "public-a",  "cidr_block": "10.0.1.0/24", "availability_zone": "eu-central-1a", "public": true},
      {"name": "private-b", "cidr_block": "10.0.2.0/24", "availability_zone": "eu-central-1b", "public": false}
    ]
  }'
```

Then `curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/v1/networks` to list
them, and `DELETE /v1/networks/{id}` to tear one down.

### Without Docker

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"
.venv/bin/pytest                 # full suite, no AWS account needed
.venv/bin/uvicorn app.main:app --reload
```

Running the server this way needs `DYNAMODB_ENDPOINT_URL` pointing at a DynamoDB Local
instance, or unset it to use real DynamoDB.

## API

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/v1/auth/token` | OAuth2 password flow → bearer token |
| `POST` | `/v1/networks` | Create a VPC with subnets |
| `GET` | `/v1/networks` | List networks, newest first (`?limit=`, `?cursor=`) |
| `GET` | `/v1/networks/{id}` | Retrieve one network |
| `DELETE` | `/v1/networks/{id}` | Delete the network and its AWS resources |
| `GET` | `/health` | Liveness, unauthenticated |

Every endpoint except `/health` and the token endpoint requires `Authorization: Bearer`.

Creating a network provisions a VPC, one subnet per entry in `subnets`, and — only if at
least one subnet is marked `public` — an internet gateway, a public route table with a
`0.0.0.0/0` default route, and an association for each public subnet. Public subnets also
get `MapPublicIpOnLaunch`.

## Deployment

Two Terraform stacks, because a pipeline cannot create the credentials and state backend
it needs in order to run.

### 1. Bootstrap — once, by a human

Creates the Terraform state bucket, the ECR repository, the GitHub OIDC provider, and the
role CI assumes. Local state, rarely changed.

```bash
cd terraform/bootstrap
terraform init
terraform apply -var="github_repository=cirrusglobal/at"
```

ECR lives here rather than in the app stack to break a circular dependency: a Lambda
function with `package_type = "Image"` cannot be created until an image exists, and CI
cannot push an image until the repository does.

Then set three **repository variables** in GitHub (Settings → Secrets and variables →
Actions → Variables) from the outputs:

| Variable | From |
|---|---|
| `AWS_ROLE_ARN` | `terraform output ci_role_arn` |
| `AWS_REGION` | `eu-central-1` |
| `TF_STATE_BUCKET` | `terraform output state_bucket` |
| `ECR_REPOSITORY` | `vpc-api` |

These are variables, not secrets — none of them is confidential, and there are no AWS
access keys to store anywhere.

### 2. Application — by CI, on merge to main

```
push to main
   ├─ lint & test        ruff + pytest (moto, no credentials)
   ├─ terraform validate  fmt + validate, -backend=false
   └─ build & deploy      OIDC → ECR push → terraform apply → smoke test
```

What gets created: the DynamoDB table, an IAM execution role, a CloudWatch log group with
14-day retention, the Lambda function, and an API Gateway HTTP API in front of it.

```bash
terraform -chdir=terraform/app output api_url
terraform -chdir=terraform/app output -raw demo_password
```

The JWT signing key and the demo password are **generated by Terraform**, not configured,
so no credential is ever committed or typed. Read the password once from the output.

### Why Lambda + API Gateway

Lambda scales to zero, so an idle deployment costs nothing — which matters on a free-tier
account. API Gateway HTTP APIs are billed purely per request with no hourly charge, unlike
an ALB at roughly $16/month just to exist.

A Lambda **Function URL** was the first choice — one fewer service, and a 15-minute
timeout instead of API Gateway's 29-second integration cap. It had to be abandoned: in
this account, public Function URLs return `403 Forbidden` regardless of configuration.
That was verified fairly thoroughly — a correct resource policy confirmed through both
`get-policy` and `get-resource-policy`, no `Deny` statements, no SCPs attached, the URL
deleted and recreated twice — while `aws lambda invoke` against the same function returned
`200`. The root cause was never established; an HTTP API is unaffected and is in any case
the more conventional front door. The 29-second cap is irrelevant here, since provisioning
completes in well under ten seconds.

The gateway uses a `$default` route so all routing stays in FastAPI rather than being
duplicated in the gateway, plus modest throttling (10 rps, burst 20) — cheap insurance on
a public endpoint that provisions billable resources.

To tear everything down: `terraform -chdir=terraform/app destroy`.

## Design decisions

**Synchronous, not async.** A VPC, its subnets, an internet gateway and route tables come
up in well under ten seconds, which fits inside any reasonable HTTP timeout. An async
job API would be the right call the moment NAT gateways enter the picture — those take
1–3 minutes each and would blow through API Gateway's 29s limit — but building a job
queue for a sub-ten-second operation is complexity with no payer.

**boto3 directly, not Terraform or Pulumi.** For a service whose entire job is this one
resource graph, an IaC engine would add a state store, a locking story, and a subprocess
or embedded runtime to own — while hiding the AWS semantics behind an abstraction. The
things IaC would have given me for free are idempotency and rollback; rollback is handled
explicitly below, and idempotency is discussed under *Known gaps*.

**Validation before any AWS call.** `app/models.py` parses every CIDR with the stdlib
`ipaddress` module and rejects: subnets outside the VPC range, subnets overlapping each
other, prefixes outside AWS's `/16`–`/28` limits, CIDRs with host bits set, and duplicate
subnet names. Surfacing a raw `botocore` error for a plan that was never going to work is
a worse experience and a slower one.

**Compensating rollback.** If subnet 3 of 4 fails, the VPC and the first two subnets
already exist — they will sit in the account, consume address space, and appear in no
API response. `VpcProvisioner` tracks every resource id as it is created and, on failure,
tears them down in reverse dependency order. Two distinct errors come out of this:

- `provisioning_failed` (502) — provisioning failed, everything was cleaned up.
- `rollback_incomplete` (500) — provisioning failed *and* cleanup failed. Resources may
  still exist. This is deliberately its own error, because it is the one case where the
  caller has to go look.

**Everything is tagged** with `ManagedBy=vpc-provisioning-api` at creation time via
`TagSpecifications`, rather than a follow-up `CreateTags` call. One fewer API call, and
no window in which a resource exists untagged — which matters, because that tag is how
orphaned resources get found later.

**DynamoDB with a GSI for listing.** Single table keyed on `network_id`. Listing uses a
global secondary index with a constant partition key and `created_at` as sort key, giving
newest-first ordering and cursor pagination at predictable cost. A `scan` would have been
fewer lines and the wrong answer.

**No NAT gateways.** ~$32/month each, several minutes to provision, and they would force
the whole design async. Private subnets here have no outbound internet path. Adding them
is a small change to `_create_public_routing` plus a move to an async job model.

## Authentication

Bearer JWTs (HS256), issued by `/v1/auth/token` against a single seeded user from the
environment. `require_auth` verifies signature, expiry, issuer and audience on every
protected route, with the algorithm list pinned — which is what prevents the `alg: none`
and HS256/RS256 confusion attacks.

**Authorization is deliberately absent.** The brief specifies it should be open to all
authenticated users, so there are no roles, scopes, or ownership checks anywhere in this
codebase. `created_by` is still recorded from the token subject, because an audit trail
costs nothing and its absence is hard to retrofit.

Self-issued tokens were chosen so a reviewer can get a working token in one curl with no
AWS account — not because Cognito is wrong. **In production**, swap `verify_token` in
`app/auth.py` for RS256 validation against a Cognito user pool's JWKS endpoint; it is the
only function that would change, and `/v1/auth/token` would be deleted entirely.

## Tests

```bash
.venv/bin/pytest -q                          # 47 tests
.venv/bin/pytest --cov=app --cov-report=term-missing   # 95% coverage
```

The whole suite runs against `moto` — no AWS account, no network, no cost. Fixtures also
inject dummy credentials so a misconfiguration cannot reach a real account.

Beyond the happy paths, the tests that matter most:

- **`test_failure_midway_through_subnets_rolls_back`** — injects a failure on subnet 2 of
  3 and asserts the account is left with no VPC and no subnets.
- **`test_failure_after_gateway_attached_rolls_back_gateway`** — fails during routing,
  once the internet gateway is already attached, to catch detach-before-delete ordering.
- **`test_failed_cleanup_reports_distinctly`** — provisioning *and* cleanup both fail;
  asserts the caller gets `rollback_incomplete`, not a misleading "rolled back".
- **`test_dns_attributes_require_two_separate_calls`** — pins a real EC2 quirk (below) so
  a future tidy-up can't merge the calls.
- **`test_validation_runs_before_any_aws_call`** — a rejected plan leaves nothing behind.

## AWS specifics worth knowing

`ModifyVpcAttribute` **rejects a call carrying both** `EnableDnsSupport` and
`EnableDnsHostnames`. They must be two calls, and support has to be enabled before
hostnames. There is a test pinning this.

A route table cannot be deleted while it has non-main associations, and an internet
gateway cannot be deleted while attached. Teardown order is: disassociate → delete route
table → detach → delete gateway → delete subnets → delete VPC.

Deletion is included even though the brief did not ask for it. The default quota is
**5 VPCs per region**, so a reviewer running the demo a few times would otherwise wedge
the account — and teardown ordering is the harder half of VPC lifecycle work anyway.

## IAM permissions

Defined in [`terraform/app/iam.tf`](terraform/app/iam.tf) — reproduced here because it is
worth reading. The runtime role gets exactly the calls `app/services/vpc.py` makes:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NetworkProvisioning",
      "Effect": "Allow",
      "Action": [
        "ec2:CreateVpc", "ec2:DeleteVpc", "ec2:DescribeVpcs", "ec2:ModifyVpcAttribute",
        "ec2:CreateSubnet", "ec2:DeleteSubnet", "ec2:ModifySubnetAttribute",
        "ec2:CreateInternetGateway", "ec2:AttachInternetGateway",
        "ec2:DetachInternetGateway", "ec2:DeleteInternetGateway",
        "ec2:CreateRouteTable", "ec2:DeleteRouteTable", "ec2:DescribeRouteTables",
        "ec2:CreateRoute", "ec2:AssociateRouteTable", "ec2:DisassociateRouteTable",
        "ec2:CreateTags"
      ],
      "Resource": "*"
    },
    {
      "Sid": "NetworkRecords",
      "Effect": "Allow",
      "Action": ["dynamodb:GetItem", "dynamodb:PutItem", "dynamodb:DeleteItem", "dynamodb:Query"],
      "Resource": [
        "arn:aws:dynamodb:*:*:table/networks",
        "arn:aws:dynamodb:*:*:table/networks/index/*"
      ]
    }
  ]
}
```

`Resource: "*"` on the EC2 block is not laziness: most `Create*` networking actions cannot
be restricted by resource, because the resource does not exist when the call is
authorised. The Terraform version therefore adds a second statement that **denies** every
delete action unless the target carries this service's `ManagedBy` tag — so the role can
create networking resources broadly, but can only destroy its own.

`dynamodb:ListTables` and `CreateTable` are absent by design: the table is managed by
Terraform, and the deployed function runs with `AUTO_CREATE_TABLE=false`.

Credentials come from the standard boto3 provider chain — an SSO profile locally, the
execution role in Lambda. There are no access keys in this repository, and CI uses GitHub
OIDC rather than stored AWS credentials.

## Known gaps

Named deliberately, so they read as decisions rather than oversights.

**No idempotency key.** A retried `POST` creates a second VPC. The fix is an
`Idempotency-Key` header with the request hash and response stored against it — the same
mechanism that would be needed for an async job model, which is why I would add both
together or neither.

**The JWT signing key is a Lambda environment variable.** Generated by Terraform and never
committed, but visible to anyone holding `lambda:GetFunctionConfiguration`, and present in
Terraform state. Secrets Manager with a fetch at cold start is the upgrade; it costs a
dozen lines and one more IAM statement.

**CI applies Terraform automatically on merge to main.** Deliberate, and defensible for a
project this size, but on a team I would gate `apply` behind a GitHub environment
approval and post the `plan` to the PR first. The `production` environment is already
declared in the workflow, so enabling a required reviewer is a one-click change.

**No CIDR allocator.** Callers choose their own ranges, and nothing prevents two networks
from overlapping. Any real multi-account deployment needs an IPAM ledger before the first
VPC peering request arrives; AWS VPC IPAM or a `cidr` column with a Postgres
`EXCLUDE USING gist` constraint both work.

**Single seeded user, no user store.** See *Authentication* — the production path is
Cognito, and the seam is one function.

**No custom domain or WAF.** The API Gateway endpoint is a raw
`*.execute-api.*.amazonaws.com` address. It carries basic stage throttling (10 rps,
burst 20), but a public endpoint that provisions billable AWS resources deserves a WAF
and per-caller quotas before it sees real traffic.
